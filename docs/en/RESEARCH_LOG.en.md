# Research log and collaboration rules

> This file lives in the repository as `docs/RESEARCH_LOG.md`. Anyone, or any AI assistant, taking over should read this page first.

## 1. Roles and permissions

| Role | Who | What it may do | What it may not do |
|---|---|---|---|
| Owner | Repository owner | Final decisions; publication/visibility, merging and releasing, history rewriting, tags | — |
| Writer | Cloud Claude | The **only** role that pushes to `main`; changes code, documents, reports | Force-push; rewrite history without the owner's consent |
| Local executor | Local Claude Code | Runs experiments on the local GPU; pushes results to a `local/...` branch, which the writer verifies and merges | Push directly to `main`; change committed experiment data |
| Research discussion | GPT (web) | Designs experiments, interprets results, reviews plans | Write to the repository |
| Auditors | GPT (web, read-only), DSH (local, read-only clone) | Independently re-check code, data, conclusions | Push; modify the repository under audit; reuse the clone of the previous round |

## 2. Rules

1. At any one time only one role writes to `main`.
2. Without the owner's consent, do not rewrite git history and do not force-push.
3. **Preregistration**: before each round of experiments starts, write the hypotheses, metrics, training seeds and the test set used into `docs/` and commit them. Interpretations obtained after seeing the data are labelled "exploratory".
4. **Held-out test set**: the currently public test seeds (10000–10299) have been looked at many times and are used only to reproduce old conclusions. New conclusions must use new seeds or a new map that have never taken part in any decision, and must be used once only. For the sealed test seeds of the preregistered study see `docs/prereg/README.md`; the default formal entry point `scripts/prereg.py final-eval` (integrity manifest plus an explicit `--unseal`) guarantees: without a manifest that passed verification the sealed seeds are not read, and the covered paths of training and model selection are constrained by test guards. The low-level Python API (constructing the token directly, calling the evaluation function), the public seed constants and modifications to the source code do **not** provide a guarantee that cannot be bypassed: the "sealing" here is protocol-based (freeze commit, manifest hash, one-shot use and traces), it guards against mistakes and is not a security boundary, and it must not be written as "only final-eval can read it".
5. For each round record: code version (commit), configuration, results directory, interruptions, failures. Keep failed results and refuted conclusions.
6. At the end of each stage ask the auditors to re-check independently from a fresh clone, before going on to the next stage.
7. Privacy (**new rule for public content**): content newly added to the public repository from now on must not contain local paths, personal information, instruction files addressed to AI assistants, or the original text of auditor reports. **Accepted legacy items** (the owner decided not to touch them): container paths in old committed logs; the internal prompt files that have been deleted in the history; the system-information lines in early reports (the device-model table of `results_gpu/LOCAL_RUN_REPORT.md`).

## 4. Known limitations (updated with the stages)

- Only 3 training seeds per cell, and the confidence intervals do not contain the training-seed variance. (This is a limitation of the **old experiments**. The current preregistered plan has 5 training seeds per cell, with intervals in units of differences over training seeds; **no new results have been produced yet**.)
- A single map; the `hard` scenario only changes the ghost chase probability, not the map.
- The two experiment sets (12 wan steps CPU, 30 wan steps GPU) are two runs of the same code and hyperparameters and do not constitute a reproduction by an independent implementation.
- Evaluation results on the GPU differ when recomputed on another device (about 0–30% of the test episodes differ episode by episode), so cross-device comparisons need a fixed evaluation device.

## 5. Technical records

- **Variance path (specification revised)**: the variance/standard deviation of the analysis script uses exact rationals (`fractions.Fraction`, computed from integer sums) and then takes the square root in float64; the final specification adopts this one path, there is no longer a `math.fsum` path, and text and implementation agree. (Previously noted as "difference from the specification text, to be revised".)
- **Analyzer error priority**: the per-file checks are enumerated in CSV row order, and within one run in the order last/standard → best/standard → last/hard (previously endpoint first); global stages 1–4 come before any record, then steps 5–7 are done in turn inside each file. The final specification §2.3 explicitly adopts this order ("not step 5 on everything first"), and it is fixed by `test_analysis_error_order.py` (`9846864`).

- **Validation de-duplication applies to all training paths**: when the training budget falls exactly on an evaluation boundary, the "final validation" is no longer repeated for the same weights (with 30 wan steps and an evaluation every 2 wan steps there are 15 validations, not 16). The committed old runs (`results/`, `results_gpu/`) predate this change and are not affected; their logs still have the duplicated last row. **If an old configuration is re-run with the new code in the future, the validation rows will be one fewer than in the old logs**; the selection of best does not change (tested: same weights, updated only when strictly greater).
- **Peak memory on Windows** (the ctypes implementation in `pacman_rl/provenance.py`, commit `c4bd147`) has been confirmed on real Windows: `peak_memory()` returns positive numbers and `peak_memory_error` is empty (working set about 508.9 MB, commit about 1500 MB), and the full tests on Windows all pass. Previously `9e46da1` returned `None` on Windows because of a 64-bit pseudo-handle overflow; the cloud could not reproduce it, and it was found by the local executor.
- **The two smoke profiles (quick, load) are independent of each other**: run names, report files and resume-check directories all carry the profile name (see `docs/prereg/README.md`); previously they shared run names, and `load` would skip the same-named runs left by `quick` and overwrite their report.
- **Window record B1/B2 (descriptive, secondary, adopted by the owner, on for 30/30)**: B1 = the proportion of windows in which the subsequent actions deviate from the greedy action selected at that time; B2 = co-occurrence of death events and deviations of subsequent actions (a **descriptive co-occurrence metric**, not a design change, not called "contamination" or "wrong attribution", it does not identify the size of the bias, and does not enter H1/H2). Implementation: `pacman_rl/window_diag.py` (recorder), `dqn.train(window_diagnostics=)` / `--window-diagnostics` (the switch is not a configuration field, the frozen configuration and matrix.csv were not changed), `scripts/window_diagnostics_summary.py` (summary and a separate `window_diagnostics_seal.json`, which verifies the freeze identity from `53688cd` on). On CPU the on/off comparison is identical, and no extra forward passes/random numbers/synchronisation is proven by tests. Local A1000 (executor's report, not reproduced by the cloud; `6023b1a` baseline, off/on/on/off): median wall-clock overhead about −0.6%, peak working set +1.5 MB, 4 groups of final weight hashes identical; since then `dqn.py` has only had `newline` argument changes. **The freeze candidate version (all architectures, full replay, formal budget) still has to be re-tested**; if it does not meet the thresholds, B1/B2 is postponed and no training parameter is changed. The implementer and the test author are the same AI, and hand-calculated expectations are not an independent manual audit.
- **Freeze process (the repository-side mechanisms as of `2ee5089`; for details see the final plan §7 and hand-over §5, not copied here)**: C (code commit) / F (freeze commit) identity, F may only contain the 6 freeze-material files (`61e7b0c`); the freeze binding check shared by the training entry point and the final-evaluation entry point (`4761265`); `.gitattributes` sets `-text` on the frozen files and requires file-by-file checking on a fresh clone of F on the formal machine (`be1e071`; the Windows fresh-clone acceptance is done by the local executor); the dependency snapshot `docs/prereg/dependency_lock.txt` is generated by the local executor, committed with C, and F may not add or change it (`10f0971`); environment evidence and `protocol_evidence`, and the formal analysis verifies C/F and the current repository before the statistics (`1268541`, `cdc0246`); for the external freeze record (GitHub Release original asset), the third-party receipt and the freeze-day order of "store first, then launch" see section D of `docs/prereg/FREEZE_CHECKLIST.md`. These are mechanisms and processes, not an executed freeze; manual sign-offs and the external record are still open.
- **Disclosure of the rehearsals before the freeze (provided by the owner, not verified by the cloud)**: when rehearsing the process in a throw-away clone, the local executor really started `res4`, n=1 of formal seed block 100 several times, each time for at most about 75 seconds, and once it reached the first validation point and did one early-model validation on `prereg_val`. The products stayed in the throw-away directory, are not merged into the formal 30 runs, their weights/checkpoints/logs are not reused, and they were not used to select an algorithm, hyperparameters, a model, a machine or a formal attempt. "Formal run" means a run after the freeze gate is completed and approved by the owner; it is not claimed that these seeds had never been started before; `prereg_val` may be used for model selection, and this validation does not amount to having read the sealed test set (the cloud has not verified the complete access history of the sealed test set). The number of times, commands, start and end times, steps and validation status are archived according to the records available, unknown items are marked unknown, and no logs are fabricated. The matrix, the seeds and H1/H2 do not change because of this.
